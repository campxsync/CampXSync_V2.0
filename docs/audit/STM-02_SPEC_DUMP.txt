1. Executive Summary
STM-02 manages the admissions application lifecycle from application creation through completeness checks, eligibility validation, document review, departmental evaluation, admission decision, offer, acceptance/decline/expiry and handover to student enrolment. It coordinates these steps while relying on existing platform capabilities for identity, academic reference data, payment processing, notifications, document storage, audit and downstream student creation.
The proposed implementation is a Spring Boot REST microservice behind the existing shared API Gateway, using PostgreSQL/Supabase for transactional records. Admission rules should be configurable and versioned by tenant/programme/intake. External integrations must be idempotent, auditable and fail safely. STM-02 must not become a second source of truth for student profile, programme catalogues, payment ledger, IAM credentials or enrolment.
1.1 Goals
Provide applicants with an accessible, resumable, multi-step application process.
Allow authorized admissions staff and reviewers to validate eligibility, inspect documents, record assessments and make auditable decisions.
Support institution/programme/intake-specific application windows, eligibility rules, required documents, fees and review workflows.
Prevent duplicate applications and duplicate student creation under concurrent requests and retries.
Integrate securely with STM-01, ACD, Finance/payment gateway, document storage/verification, notification, audit and STM-03 enrolment.
Support tenant isolation, field-level permissions, configurable workflow and analytics without leaking personal data.
1.2 Non-goals
Canonical student identity/profile ownership — STM-01.
Programme, department, academic year and course catalogue ownership — existing ACD/core reference domains.
Payment ledger, refunds and reconciliation source of truth — Finance; STM-02 stores only application payment reference/status summary where required.
Authentication, credentials and roles — IAM.
Enrolment records and academic status after acceptance — STM-03 or the existing designated enrolment service.
Document binaries, general-purpose notifications, generic workflow engine or audit platform — shared services, if available.
Creating proposed tables before schema ownership and duplication checks.

5. Application Lifecycle / State Machine
This is a proposed workflow, not an assertion that these states already exist. Institutions may configure different steps, but each transition must be explicit, permission-checked, timestamped and auditable. Payment status is a separate dimension and must not be confused with application status.
5.1 State-transition requirements
Every transition has an authorized actor or system principal, a reason code where required, timestamp, tenant, correlation ID and rule/workflow version.
Reject client attempts to patch status directly; use explicit action endpoints and server-side transition validation.
Use optimistic concurrency or equivalent to prevent two reviewers overwriting each other.
Notifications are triggered after the state change commits, not before.
Payment state and document-verification state are independent sub-workflows.
Retries and repeated webhooks must be idempotent.

10. API Gateway, Tenant Isolation and RLS
Use the existing shared API Gateway and IAM; no second gateway or parallel auth implementation.
Resolve tenant context from trusted claims/platform context; reject absent or conflicting tenant context.
Enforce route permission at gateway and application/action permission in STM-02; database RLS and grants provide defense in depth.
Applicants may access only their own application and safe applicant-facing status/document views.
Reviewers may access only assigned applications and permitted fields; department/programme scope must be checked on every request.
Never trust client-supplied reviewer ID, tenant ID, decision actor, payment success, verification status or offer status.
Payment success must be confirmed through a trusted provider/Finance callback or status API with signature/authorization checks and replay protection.
RLS policies must fail closed without tenant context and must not allow cross-tenant joins or caller-controlled tenant impersonation.
Test SELECT/INSERT/UPDATE and all relevant relationship joins using real non-production roles across at least two tenants.

14. Sequence Flows
14.1 Applicant submits an application
Applicant authenticates and opens an application for an available ACD programme/intake.
Gateway validates identity, tenant context and route access; STM-02 checks applicant ownership and application window.
STM-02 validates required fields and the applicable versioned eligibility/completeness rules.
Document adapter verifies required metadata/references; binary upload is handled by approved storage.
STM-02 commits application state and status history atomically, then publishes an event through the approved reliable mechanism.
Notification service sends confirmation after commit; applicant receives application number and safe status.
Review/eligibility workflow proceeds asynchronously where required.
14.2 Reviewer decides and offer is accepted
Authorized reviewer retrieves only assigned application data and records an assessment against the configured rubric.
Decision workflow verifies permissions, required approvals, current state and version before committing the decision.
Offer is created with versioned terms and validity window; applicant is notified.
Applicant accepts only while the offer is valid; a transaction prevents duplicate acceptance.
STM-02 requests STM-01 identity linkage/creation according to the agreed lifecycle policy and waits for an idempotent result.
STM-02 sends enrolment handover to STM-03; retries and reconciliation handle downstream failures without duplicating the student or enrolment.
Application is marked as handed over only when the downstream confirmation contract is satisfied.
15. Security, Privacy and Compliance
Collect only admissions data needed for a stated institutional purpose and configured programme criteria.
Limit applicant visibility to their own application, uploaded documents and safe decision/status information.
Restrict reviewer comments, scores, identity documents, financial details and verification signals to authorized roles.
Use TLS, approved secrets management, least-privilege database grants and safe object-storage access.
Redact tokens, OTPs, document contents, payment details and unnecessary PII from logs and events.
Audit application submission, document verification, review changes, decisions, offer issuance/acceptance, payment status changes and identity/enrolment handover.
Validate document MIME/type/size, malware scanning where available, private access and expiry/retention.
Protect callbacks with signature validation, timestamp/replay checks, idempotency and reconciliation.
Apply retention, correction, appeal and deletion policies according to institution and legal requirements.
16. Validation and Error Rules
17. Testing Strategy and Acceptance Criteria
17.1 Unit and component tests
Application state machine permits only configured transitions and rejects direct status patches.
Eligibility rules are versioned, deterministic for fixed inputs and produce safe reason codes.
Submission validates application window, required fields, required documents and declarations.
Offer expiry and concurrent acceptance cannot produce two successful acceptances.
Duplicate create/submit/payment callback/event retries remain idempotent.
Review permission, assignment scope and separation-of-duties rules are enforced.
Payment adapter never trusts client status and handles provider retries/timeouts.
Identity creation/linkage and enrolment handover retries do not create duplicate records.
Event payloads redact sensitive fields and include correlation/tenant identifiers.
17.2 Integration and security tests
Cross-tenant application reads, updates, document references, searches and reviewer queues are denied.
Missing tenant context fails closed at service and RLS layers.
Applicants cannot view another applicant's application, reviewer comments or restricted document metadata.
Unauthorized roles cannot verify documents, score, approve, reject, issue offers or alter payment status.
RLS and grants are tested with the actual non-production application role, not only privileged admin credentials.
Payment callback signature/replay protection and reconciliation paths are tested.
Duplicate/out-of-order events and downstream outage recovery are tested.
Migration/rollback tests run only in approved non-production staging after explicit environment verification and write approval.
17.3 Acceptance criteria
Read-only audit identifies existing admissions tables, APIs, services, constraints, RLS and reusable workflow/payment/document capabilities.
No duplicate student identity, programme catalogue, Finance ledger, IAM, notification, audit or document binary store is introduced.
Applicant can create, resume, submit and track only their own application.
Staff can review and decide only within assigned tenant/programme/department scope.
State changes, eligibility results, review decisions, offer lifecycle and payment references are auditable.
Offer acceptance triggers idempotent STM-01 and STM-03 integration with recoverable failure handling.
All tenant-isolation and authorization tests pass against non-production data and roles.
Physical schema/API changes follow existing CampXSync conventions and are reviewed before execution.
No production database is accessed or modified during design.
