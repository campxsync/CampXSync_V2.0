## 3. Top Forensic Findings

### Finding 1: The Headline "458 Tables" Literally Includes Child Partitions
The headline count of 458 application tables in `CampXSync-Architecture-Dev` comprises:
- **422 Ordinary Standalone Tables** (`relkind = 'r' AND NOT relispartition`)
- **6 Partitioned Parent Tables** (`relkind = 'p'`)
- **30 Child Partition Tables** (`relispartition = true`)
- **Total Tables in `pg_tables`:** **458**  
The claim that `20_tables.sql` "creates all 458 tables" is physically incorrect: `20_tables.sql` creates only the **428 base tables**; the 30 child partitions are generated by `45_partitions.sql`.

### Finding 2: Root Causes of Baseline Count Discrepancies Resolved
- **Constraints (2,689 total):** 458 PKs (428 base + 30 inherited), 1,239 FKs (1,194 base + 45 inherited), 403 Unique, 585 Check, 3 Exclusion, 1 Trigger constraint. Baseline per-schema rows mis-summed (+6 FK, +6 UQ, -46 CK); catalog sums to 2,689 perfectly.
- **Triggers (799 total):** 784 base triggers + 15 inherited partition triggers (`audit.trg_immutable`). Baseline table listed 6 triggers for `audit` instead of 29, causing the 21-trigger shortfall (778 vs 799).
- **Indexes (2,026 vs 2,521):** The baseline figure of 2,521 included **495 internal `pg_toast` table indexes**. True user-space application indexes number **2,026** (1,926 base + 100 on child partitions).
- **RLS Policies (1,545 total):** Baseline column totals omitted policies with `cmd = 'ALL'`. With 19 platform admin policies isolated, the counts reconcile cleanly: 430 SELECT + 392 INSERT + 352 UPDATE + 352 DELETE + 19 ALL = **1,545**.

### Finding 3: Discovery of Untracked Live Event Trigger
A live custom event trigger and trigger function exist on `CampXSync-Architecture-Dev` with **zero representation in the repository**:
- **Event Trigger:** `enable_rls_on_new_tables` (`ddl_command_end`, tags: `['CREATE TABLE']`, owner: `postgres`)
- **Function:** `sys.enable_rls_on_new_tables()`
- **Behavior:** Dynamically executes `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` whenever a table is created in schemas `audit`, `cam`, `hrm`, or `lms`. This explains why child partitions had RLS enabled in dev despite `sys.ensure_partitions` lacking RLS logic.

### Finding 4: Timetable Exclusion Constraints Pre-existed Waves 0–10
The assertion in the baseline README that GiST exclusion constraints (`ex_tte_employee`, `ex_tte_section`, `ex_tte_room`) were introduced during Waves 0–10 is **refuted**. They were defined in bootstrap script `Documentation/DatabaseDesign/Supabase/Scripts_V3.0/50_triggers.sql`, lines 923–934 from the initial commit. Wave 5 explicitly verified them with *"Zero DDL migrations required"*.

### Finding 5: Context Binding Alignment & `FORCE RLS` Inefficacy
- **Tenant Context Alignment:** Java domain services set `SELECT set_config('request.jwt.claims', ?, true)` on JDBC connections. `core.current_tenant_id()` delegates to `auth.jwt()`, which reads `request.jwt.claims`. GUC names match 100%. `core.current_tenant_id()` is a pure in-memory SQL expression without table joins, eliminating any RLS recursion risk.
- **`FORCE RLS` Practical Effect:** The 4 tables with `relforcerowsecurity = true` (`stu.students`, `core.persons`, `stu.guardianships`, `acd.batch_students`) are owned by `postgres`. Because `postgres` has `rolbypassrls = true`, PostgreSQL bypasses RLS on them. Because `campx_app_server` is not the owner and lacks `BYPASSRLS`, standard `ENABLE RLS` already constrains it. Consequently, `FORCE RLS` has **zero practical effect** under the current live role setup.
