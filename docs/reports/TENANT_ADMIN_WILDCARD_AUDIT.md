## 2. Executive Summary of Key Facts

1. **Isolation in Practice:** While `TENANT_ADMIN` is provisioned with the wildcard permission `*` in template catalogs across all 49 tenants, it is **active for only 1 user in 1 tenant** (`DEV_TEST_TENANT`). The other 48 production/test tenant instances operate purely under `COLLEGE_ADMIN` (R04) and `INSTITUTION_ADMIN` (R03).
2. **Onboarding Disconnect:** The college onboarding workflow in `PostgresCollegeOnboardingRepository.java` provisions the first tenant user as `COLLEGE_ADMIN`, **never** as `TENANT_ADMIN`. Consequently, `TENANT_ADMIN` cannot be spawned through normal application workflows.
3. **Impenetrable Role Escalation:** `iam.role_grant_rules` and the `iam.guard_role_assignment` trigger strictly prevent privilege escalation: an `INSTITUTION_ADMIN` or `COLLEGE_ADMIN` cannot grant `TENANT_ADMIN`. Because of the self-revocation block, the sole existing `TENANT_ADMIN` cannot accidentally remove themselves without superuser access.
4. **Scope of the Wildcard `*`:** The wildcard `*` confers universal access to all permission-guarded tables and business operations inside that tenant, but it does **not** grant permission to assign arbitrary system roles—system role grants remain strictly constrained by the literal grant matrix in `iam.role_grant_rules`.

## 3. NOT VERIFIED

- **Direct Superuser Bypass via API Routes:** When frontend API routes connect using direct superuser credentials (`postgres`), `iam.is_privileged_session()` returns `true`, completely bypassing RLS and all IAM permission checks, rendering the database-level `TENANT_ADMIN` constraints moot for those specific direct-connect routes. The extent to which legacy UI routes take this bypass path remains uninstrumented in live traffic.
